## Решение 1: API Gateway

### Сравнительная таблица возможностей API Gateway

| Критерий | Apache APISIX | Kong (OSS) | Traefik | Envoy |
|---|---|---|---|---|
| **Маршрутизация запросов** | + (radixtree, динамическая через etcd) | + (через БД PostgreSQL/Cassandra) | + (автообнаружение) | + (через xDS API) |
| **Аутентификация** | + (JWT, OIDC, key-auth, mTLS) | + (JWT, API keys, mTLS; OIDC — Enterprise) | + (middleware) | + (HTTP-фильтры) |
| **Терминация HTTPS** | + | + | + (Let's Encrypt) | + |
| **Горячая перезагрузка** | + (мс, без перезапуска) | Частичная (опрос БД 5–10 сек) | + | + |
| **Хранилище конфигурации** | etcd | PostgreSQL / Cassandra | Файлы / KV | xDS API |
| **Плагины** | 100+; Lua, Java, Go, Python, Wasm | ~60; Lua, Go | ~30; Go | ~30; C++, Wasm |
| **Протоколы** | HTTP/3, gRPC, WebSocket, MQTT, TCP, UDP | HTTP, gRPC, TCP, UDP, WebSocket | HTTP, gRPC, TCP, UDP | HTTP/3, gRPC, TCP |
| **Производительность (QPS)** | 23 000 QPS/ядро, 0.2 мс | Высокая | Средняя | Высокая |
| **Лицензия** | Apache 2.0 (ASF) | Apache 2.0 (OSS) | MIT | Apache 2.0 |
| **Вендор-локин** | Низкий | Средний | Низкий | Низкий |

---

### Обоснование выбора: Apache APISIX

**Apache APISIX** выбран в качестве решения для API Gateway по следующим причинам:

1. **Полное соответствие требованиям** — маршрутизация, аутентификация (JWT, OIDC, key-auth) и терминация HTTPS реализованы встроенными плагинами.

2. **Высокая производительность** — 23 000 QPS на ядро с задержкой 0.2 мс, что вдвое превосходит Kong в бенчмарках с плагинами. Архитектура на etcd исключает зависимость от БД на data path.

3. **Богатая экосистема** — более 100 встроенных плагинов с поддержкой разработки на Lua, Java, Go, Python и Wasm. В отличие от Kong, все плагины доступны в открытой версии.

4. **Динамическая конфигурация** — изменения маршрутов применяются за миллисекунды через etcd watch без перезапуска шлюза.

5. **Отсутствие вендор-локина** — проект Apache Software Foundation с лицензией Apache 2.0 гарантирует независимость от коммерческих вендоров.

6. **Поддержка современных протоколов** — HTTP/3 (QUIC), gRPC, WebSocket и MQTT.

## Решение 2: Брокер сообщений

### Сравнительная таблица возможностей брокеров сообщений

| Критерий | Apache Kafka | RabbitMQ | Apache ActiveMQ | IBM MQ |
|---|---|---|---|---|
| **Кластеризация** | + (партиции, репликация) | + (HA-кластер) | + | + |
| **Хранение на диске** | + (persistent, настраиваемое TTL) | + | + | + |
| **Скорость работы** | Высочайшая (млн msg/сек) | Высокая | Средняя | Средняя |
| **Форматы сообщений** | Kafka protocol, REST, Connect | AMQP, MQTT, STOMP | JMS, AMQP, MQTT, STOMP | JMS, MQTT, REST, AMQP |
| **Разделение прав** | + (ACL, SASL, SSL) | + (ACL) | + (JAAS, TLS) | + (ролевая модель) |
| **Простота эксплуатации** | Средняя | Высокая | Средняя | Низкая |
| **Модель сообщений** | Потоковая (commit log) | Очередная | Очередная | Очередная |
| **Воспроизведение (replay)** | + (сдвиг offset) | − | − | − |
| **Dead Letter Queue** | − | + | + | + |
| **Транзакции** | + | + | + | + |
| **Лицензия** | Apache 2.0 | Apache 2.0 / MPL | Apache 2.0 | Платная |

---

### Обоснование выбора: Apache Kafka

**Apache Kafka** выбран в качестве брокера сообщений по следующим причинам:

1. **Полное соответствие требованиям** — кластеризация, дисковое хранение, высокая скорость, мультипротокольность и ACL-разграничение доступа.

2. **Высочайшая производительность** — миллионы сообщений в секунду благодаря sequential I/O и zero-copy архитектуре, что критично для пиковых нагрузок интернет-магазина.

3. **Горизонтальное масштабирование** — партиционирование позволяет линейно увеличивать пропускную способность добавлением брокеров.

4. **Возможность воспроизведения (replay)** — хранение сообщений в течение настраиваемого периода (по умолчанию 7 дней) позволяет перепроцессировать данные при сбоях или для аналитики — важное преимущество перед очередями.

5. **Интеграция с Big Data** — Kafka является стандартом де-факто для streaming-платформ (Kafka Streams, Flink, Spark), что дает возможность строить системы реального времени для аналитики заказов и рекомендаций.

6. **Зрелая экосистема** — активное комьюнити, инструменты мониторинга (Prometheus, Grafana), поддержка Kubernetes через Strimzi, низкая стоимость владения.

7. **Гибкость** — возможность комбинировать потоковую и очередную модели через consumer groups для адаптации под различные сценарии взаимодействия сервисов.

---

### Альтернативы по брокерам

- **RabbitMQ** — проще в эксплуатации и настройке, лучше подходит для небольших проектов или сценариев с маршрутизацией на основе сложных правил (headers, exchanges). Но уступает Kafka в производительности и возможности replay.

- **IBM MQ** — Enterprise-решение для финансового сектора с высокой надежностью, но сложное в эксплуатации и требует платной лицензии.

> **Итоговый вывод**: Для интернет-магазина с растущей нагрузкой и потребностью в аналитике в реальном времени Kafka — оптимальный выбор по соотношению производительность/стоимость/функциональность.



## Задача 3: API Gateway * (необязательная)

### Есть три сервиса:

**minio**
- хранит загруженные файлы в бакете images,
- S3 протокол,

**uploader**
- принимает файл, если картинка сжимает и загружает его в minio,
- POST /v1/upload,

**security**
- регистрация пользователя POST /v1/user,
- получение информации о пользователе GET /v1/user,
- логин пользователя POST /v1/token,
- проверка токена GET /v1/token/validation.

### Необходимо воспользоваться любым балансировщиком и сделать API Gateway:

**POST /v1/register**
1. Анонимный доступ.
2. Запрос направляется в сервис security POST /v1/user.

**POST /v1/token**
1. Анонимный доступ.
2. Запрос направляется в сервис security POST /v1/token.

**GET /v1/user**
1. Проверка токена. Токен ожидается в заголовке Authorization. Токен проверяется через вызов сервиса security GET /v1/token/validation/.
2. Запрос направляется в сервис security GET /v1/user.

**POST /v1/upload**
1. Проверка токена. Токен ожидается в заголовке Authorization. Токен проверяется через вызов сервиса security GET /v1/token/validation/.
2. Запрос направляется в сервис uploader POST /v1/upload.

**GET /v1/user/{image}**
1. Проверка токена. Токен ожидается в заголовке Authorization. Токен проверяется через вызов сервиса security GET /v1/token/validation/.
2. Запрос направляется в сервис minio GET /images/{image}.

### Ожидаемый результат

Результатом выполнения задачи должен быть docker compose файл, запустив который можно локально выполнить следующие команды с успешным результатом.
Предполагается, что для реализации API Gateway будет написан конфиг для NGinx или другого балансировщика нагрузки, который будет запущен как сервис через docker-compose и будет обеспечивать балансировку и проверку аутентификации входящих запросов.
Авторизация
curl -X POST -H 'Content-Type: application/json' -d '{"login":"bob", "password":"qwe123"}' http://localhost/token

**Загрузка файла**
