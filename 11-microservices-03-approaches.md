# Предложение по организации процесса разработки

## Решение: GitLab (единая платформа)

Предлагается использовать **GitLab** как единую комплексную платформу, объединяющую все необходимые компоненты для разработки.

---

## Соответствие требованиям

| Требование | Реализация в GitLab |
|---|---|
| Облачная система | GitLab.com (SaaS) или саморазмещаемая установка в облаке |
| Система контроля версий Git | Встроенный Git-репозиторий |
| Репозиторий на каждый сервис | Отдельные проекты для каждого микросервиса |
| Запуск сборки по событию из Git | Автоматический запуск по push, merge request, tag |
| Запуск сборки по кнопке с параметрами | Ручной запуск через UI/API с передачей параметров. CI/CD inputs с валидацией типов |
| Привязка настроек к сборке | Переменные окружения на уровне job, pipeline, группы или проекта |
| Шаблоны для различных конфигураций | Механизмы `extends`, `include`, `parallel:matrix`, шаблоны из каталога |
| Безопасное хранение секретов | Встроенное хранилище переменных (protected/masked). Интеграция с HashiCorp Vault через OIDC |
| Несколько конфигураций из одного репозитория | `rules` + `variables` для условного переопределения параметров, `parallel:matrix` для генерации множества job |
| Кастомные шаги при сборке | Любые shell-скрипты в секции `script`, поддержка Bash и PowerShell |
| Собственные Docker-образы для сборки | Указание любого образа через `image:` в каждом job |
| Агенты сборки на своих серверах | GitLab Runner устанавливается на любые платформы: Linux, Windows, macOS, Kubernetes |
| Параллельный запуск нескольких сборок | Jobs внутри stages выполняются параллельно. `concurrent` ограничивает общее количество одновременно выполняемых job |
| Параллельный запуск тестов | Механизм `parallel:matrix` для распараллеливания тестов по разным параметрам. Встроенная поддержка Knapsack для балансировки нагрузки между тестовыми job |

---

## Обоснование выбора

1. **Единая платформа** — GitLab предоставляет всё необходимое «из коробки»: репозиторий, CI/CD, реестр контейнеров, мониторинг. Не требуется интеграция нескольких разрозненных инструментов.

2. **Гибкая конфигурация** — Поддерживаются все заявленные сценарии: автоматический и ручной запуск, шаблоны, условные конфигурации, кастомные образы.

3. **Безопасность** — Секреты хранятся в защищённых переменных. Поддерживается интеграция с Vault через OIDC без необходимости хранить долгосрочные ключи.

4. **Масштабируемость** — GitLab Runner поддерживает автомасштабирование на публичных облаках (AWS, GCP, Azure) и в Kubernetes. Можно развернуть собственных агентов для изоляции окружений.

5. **Простота эксплуатации** — Единая точка управления, прозрачная настройка через `.gitlab-ci.yml`, активное сообщество и обширная документация.

### Решение 2: Логи

# Предложение по организации сбора и анализа логов

## Решение: PLG Stack (Promtail + Loki + Grafana)

Предлагается использовать стек **PLG** (Promtail, Loki, Grafana) как легковесное и эффективное решение для сбора, хранения и анализа логов в микросервисной архитектуре.

---

## Соответствие требованиям

| Требование | Реализация в PLG Stack |
|---|---|
| Сбор логов в центральное хранилище | Promtail собирает логи со всех хостов и отправляет в Loki |
| Сбор логов из stdout | Promtail поддерживает сбор логов из stdout контейнеров [citation:6] |
| Гарантированная доставка | Promtail использует disk-буферизацию при сбоях, обеспечивая «at least once» доставку [citation:5][citation:7] |
| Поиск и фильтрация по логам | Loki поддерживает мощный язык запросов LogQL и фильтрацию по лейблам [citation:4] |
| Пользовательский интерфейс для разработчиков | Grafana предоставляет удобный веб-интерфейс для поиска и анализа логов [citation:4][citation:10] |
| Ссылка на сохранённый поиск | Grafana позволяет сохранять запросы и делиться ссылками на них [citation:10] |
