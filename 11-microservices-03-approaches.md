# Предложение по организации процесса разработки

## Решение: GitLab (единая платформа)

Предлагается использовать **GitLab** как единую комплексную платформу, объединяющую все необходимые компоненты для разработки.

---

## Соответствие требованиям

| Требование | Реализация в GitLab |
|---|---|
| Облачная система | GitLab.com (SaaS) или саморазмещаемая установка в облаке |
| Система контроля версий Git | Встроенный Git-репозиторий |
| Репозиторий на каждый сервис | Отдельные проекты для каждого микросервиса |
| Запуск сборки по событию из Git | Автоматический запуск по push, merge request, tag |
| Запуск сборки по кнопке с параметрами | Ручной запуск через UI/API с передачей параметров. CI/CD inputs с валидацией типов |
| Привязка настроек к сборке | Переменные окружения на уровне job, pipeline, группы или проекта |
| Шаблоны для различных конфигураций | Механизмы `extends`, `include`, `parallel:matrix`, шаблоны из каталога |
| Безопасное хранение секретов | Встроенное хранилище переменных (protected/masked). Интеграция с HashiCorp Vault через OIDC |
| Несколько конфигураций из одного репозитория | `rules` + `variables` для условного переопределения параметров, `parallel:matrix` для генерации множества job |
| Кастомные шаги при сборке | Любые shell-скрипты в секции `script`, поддержка Bash и PowerShell |
| Собственные Docker-образы для сборки | Указание любого образа через `image:` в каждом job |
| Агенты сборки на своих серверах | GitLab Runner устанавливается на любые платформы: Linux, Windows, macOS, Kubernetes |
| Параллельный запуск нескольких сборок | Jobs внутри stages выполняются параллельно. `concurrent` ограничивает общее количество одновременно выполняемых job |
| Параллельный запуск тестов | Механизм `parallel:matrix` для распараллеливания тестов по разным параметрам. Встроенная поддержка Knapsack для балансировки нагрузки между тестовыми job |

## Обоснование выбора

1. **Единая платформа** — GitLab предоставляет всё необходимое «из коробки»: репозиторий, CI/CD, реестр контейнеров, мониторинг. Не требуется интеграция нескольких разрозненных инструментов.

2. **Гибкая конфигурация** — Поддерживаются все заявленные сценарии: автоматический и ручной запуск, шаблоны, условные конфигурации, кастомные образы.

3. **Безопасность** — Секреты хранятся в защищённых переменных. Поддерживается интеграция с Vault через OIDC без необходимости хранить долгосрочные ключи.

4. **Масштабируемость** — GitLab Runner поддерживает автомасштабирование на публичных облаках (AWS, GCP, Azure) и в Kubernetes. Можно развернуть собственных агентов для изоляции окружений.

5. **Простота эксплуатации** — Единая точка управления, прозрачная настройка через `.gitlab-ci.yml`, активное сообщество и обширная документация.

### Решение 2: Логи

# Предложение по организации сбора и анализа логов

## Решение: PLG Stack (Promtail + Loki + Grafana)

Предлагается использовать стек **PLG** (Promtail, Loki, Grafana) как легковесное и эффективное решение для сбора, хранения и анализа логов в микросервисной архитектуре.

---

## Соответствие требованиям

**Сбор логов в центральное хранилище со всех хостов, обслуживающих систему**

Promtail устанавливается на каждый хост и собирает логи со всех запущенных контейнеров, после чего отправляет их в центральное хранилище Loki.

**Сбор логов из stdout с минимальными требованиями к приложениям**

Приложениям достаточно писать логи в stdout, что является стандартной практикой для контейнеризированных приложений. Promtail автоматически собирает эти логи без изменения кода сервисов. Разработчикам не нужно использовать специальные библиотеки или настраивать дополнительные протоколы.

**Гарантированная доставка логов до центрального хранилища**

Promtail использует механизм disk-буферизации. При сбое сети или недоступности Loki, данные сохраняются локально на диске и отправляются повторно после восстановления соединения, что обеспечивает доставку "at least once".

**Обеспечение поиска и фильтрации по записям логов**

Loki поддерживает мощный язык запросов LogQL, который позволяет фильтровать логи по лейблам, временным диапазонам и содержимому, а также выполнять агрегации и статистические операции.

**Обеспечение пользовательского интерфейса с доступом разработчикам**

Grafana предоставляет удобный веб-интерфейс для поиска и анализа логов. Доступ можно разграничить на уровне прав пользователей, предоставив разработчикам доступ только к определённым сервисам или окружениям.

**Возможность дать ссылку на сохранённый поиск по записям логов**

Grafana позволяет сохранять запросы в виде дашбордов или ссылок, которыми разработчики могут делиться друг с другом.

Обоснование выбора

1. Минимальные требования к приложениям

Приложениям достаточно писать логи в stdout, что является стандартной практикой для контейнеризированных приложений. Promtail автоматически собирает эти логи без изменения кода сервисов. Разработчикам не нужно использовать специальные библиотеки или настраивать дополнительные протоколы.

2. Гарантированная доставка

Promtail использует механизм disk-буферизации. При сбое сети или недоступности Loki, данные сохраняются локально на диске и отправляются повторно после восстановления соединения, что обеспечивает доставку "at least once".

3. Эффективное хранение

В отличие от ELK Stack, который индексирует каждое поле и требует значительных ресурсов, Loki использует индексацию только по лейблам, что позволяет экономить до 80% ресурсов хранения.

4. Высокая скорость работы

Loki оптимизирован для работы с большими объёмами логов. Тесты показывают, что Loki быстрее обрабатывает и запрашивает большие объёмы логов, чем Elasticsearch, что критично для высокой нагрузки интернет-магазина.

5. Гибкий поиск

LogQL позволяет разработчикам создавать сложные запросы с фильтрацией по любым полям, временным диапазонам и содержимому, не уступая по функциональности Elasticsearch.

6. Совместная работа

Grafana поддерживает сохранение запросов и создание ссылок на них, что позволяет разработчикам делиться результатами поиска с коллегами.

7. Простота эксплуатации

PLG Stack проще в настройке и обслуживании, чем ELK, что снижает затраты на DevOps-поддержку.

8. Единый интерфейс мониторинга

Grafana уже используется в инфраструктуре для мониторинга и алертинга. Добавление логов в тот же интерфейс упрощает работу разработчиков и сокращает количество инструментов, которые нужно изучать.
Итоговый вывод

PLG Stack (Promtail + Loki + Grafana) является оптимальным решением для микросервисной архитектуры интернет-магазина по следующим причинам:

    Минимальные требования к разработчикам — достаточно писать логи в stdout

    Гарантированная доставка через disk-буферизацию

    Экономия ресурсов хранения и памяти

    Высокая производительность при больших объёмах данных

    Единый интерфейс с существующим мониторингом (Grafana)

    Простота эксплуатации и обслуживания

При этом решение значительно экономичнее и проще в эксплуатации, чем альтернативы, особенно в условиях высокой нагрузки.
