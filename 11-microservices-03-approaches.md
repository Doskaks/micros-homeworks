## Решение 1

# Предложение по организации инфраструктуры разработки

## Решение: GitLab CI/CD

В качестве единой платформы для обеспечения процесса разработки предлагается использовать **GitLab** (SaaS или Self-Managed), который объединяет все необходимые компоненты в одном экосистемном решении.

---

## Архитектура решения

### Основные компоненты:

1. **GitLab** — система контроля версий и центральный оркестратор CI/CD.
2. **GitLab Runners** — агенты сборки (несколько типов для разных задач).
3. **Container Registry** — встроенный реестр Docker-образов.
4. **GitLab Vault/Environment Variables** — безопасное хранение секретов.

### Схема взаимодействия:

Разработчик → Git push → GitLab → Триггер пайплайна → GitLab Runner (агент) →
→ Сборка → Тесты (параллельно) → Публикация артефактов/образов → Развертывание

---

## Соответствие требованиям

| Требование | Реализация в GitLab |
|------------|-------------------|
| **Облачная система** | GitLab.com (SaaS) или GitLab Dedicated (Single-Tenant SaaS) [citation:2]. |
| **Система контроля версий Git** | Встроенный Git-репозиторий. |
| **Репозиторий на каждый сервис** | Поддерживается — каждый микросервис в отдельном проекте. |
| **Запуск сборки по событию из VCS** | Триггеры `push`, `merge_request`, `tag` в `.gitlab-ci.yml`. |
| **Запуск сборки по кнопке с параметрами** | Ручной запуск (`when: manual`) с переменными (`variables`). |
| **Привязка настроек к каждой сборке** | Переменные окружения на уровне проекта, группы, CI/CD. |
| **Шаблоны для различных конфигураций** | `include:local` или `include:template` для переиспользования. |
| **Безопасное хранение секретов** | Защищенные переменные (маскируются в логах), интеграция с Vault. |
| **Несколько конфигураций из одного репозитория** | Разные файлы `.gitlab-ci.yml` для разных веток или правил (`rules`). |
| **Кастомные шаги при сборке** | Произвольные `script`, `before_script`, `after_script`. |
| **Собственные Docker-образы для сборки** | `image: <custom-image>` — любой образ из Container Registry. |
| **Развертывание агентов на собственных серверах** | Self-hosted GitLab Runners (любая ОС, любой облачный провайдер) [citation:3]. |
| **Параллельный запуск нескольких сборок** | Несколько `jobs` со стратегией `parallel: matrix` [citation:5]. |
| **Параллельный запуск тестов** | `parallel: matrix` или разделение тестов на несколько `jobs`. |

## Обоснование выбора

### 1. Единая платформа (DevSecOps)

GitLab предоставляет всё необходимое в одном месте: репозиторий, CI/CD, реестр образов, управление секретами, мониторинг. Это упрощает администрирование и снижает количество интеграций. Согласно документации по миграции, концепция агентов в GitLab аналогична Bamboo, а пайплайны определяются кодом — что соответствует лучшим практикам [citation:2].

### 2. Гибкость агентов сборки

GitLab Runners могут быть развернуты на любых серверах (on-premise, AWS, Azure, GCP) с поддержкой различных `executor` (Shell, Docker, Kubernetes). Это полностью соответствует требованию по развертыванию агентов на собственных серверах [citation:3].

### 3. Мощная система параллелизации

Встроенная поддержка `parallel: matrix` позволяет запускать один job с разными конфигурациями (например, тесты на разных версиях языка или ОС). Это полностью покрывает требования по параллельному запуску сборок и тестов [citation:5].

### 4. Pipeline as Code

Все пайплайны описываются в файле `.gitlab-ci.yml` в репозитории, что обеспечивает версионность и воспроизводимость. Поддерживается включение шаблонов (`include`) для переиспользования конфигураций между сервисами.

### 5. Безопасность из коробки

Защищенные переменные позволяют безопасно хранить пароли, токены и ключи доступа. Значения маскируются в логах, доступ к ним можно ограничивать на уровне окружений (environment scopes). [citation:12]

### 6. Зрелая экосистема

GitLab активно развивается, имеет большое сообщество и интеграции с большинством DevOps-инструментов (Kubernetes, Terraform, Prometheus, etc.). Это делает решение устойчивым для долгосрочного использования в крупной компании.

## Дополнительные рекомендации

- Для высоконагруженных сборок использовать **Kubernetes executor** для динамического масштабирования агентов.
- Настроить **Review Apps** для автоматического поднятия тестовых окружений на каждый Merge Request.
- Использовать **GitLab Container Registry** для хранения Docker-образов микросервисов.
